Tracing supports the Model Context Protocol (MCP) in two ways:

1. **Built-in HTTP endpoint**: every Tracing instance exposes `/api/mcp` out of the box. No extra setup, no extra process.
2. **Local stdio server**: build the `@tracing/mcp` workspace package from this repository. It is not published to npm.

Both offer the same tools for managing workspaces, projects, tasks, custom fields, comments, and labels.

To work with Tracing from a terminal or a shell script instead, use the [Tracing CLI](/cli).

## Built-in HTTP endpoint

Every Tracing API instance ships with a Streamable HTTP MCP endpoint. This is the recommended approach for self-hosted deployments.

Point your MCP client at:

```
https://tracing.example.com/api/mcp
```

With an OAuth-capable client, you will be redirected to Tracing to sign in and explicitly approve the MCP client. After approval, all MCP tools run as your authenticated user.

The endpoint implements OAuth 2.1 with PKCE for authentication. Discovery metadata is available at:

- `/.well-known/oauth-protected-resource/api/mcp`
- `/.well-known/oauth-authorization-server/api`

The endpoint serves both MCP protocol eras without server-side sessions. Modern
`2026-07-28` requests are self-contained; 2025-era clients still send
`initialize`, but Tracing does not issue a session ID. See [MCP protocol
reference](/core/integrations/mcp-stateless) for transport behavior, proxy
requirements, and request limits.

## Stdio package

The `@tracing/mcp` package runs a local stdio MCP server and authenticates with Tracing using device authorization. Use this when your MCP client requires stdio transport.

### Prerequisites

- Node.js 24 or newer
- A running Tracing API
- Access to the Tracing web app to approve device login

Build from the repository using its locked dependencies:

```bash
pnpm install --frozen-lockfile
pnpm --filter @tracing/mcp build
TRACING_API_URL=https://tracing.gofigureapp.io node packages/mcp/dist/index.js serve
```

Configure a stdio client to run `node` with the absolute path to
`packages/mcp/dist/index.js` followed by `serve`, and set `TRACING_API_URL` in
that client's environment. The built-in HTTP endpoint is simpler for clients
that support it. To generate that configuration interactively, run
`node packages/mcp/dist/index.js install` from your source checkout. The
installer records the current Node executable and the local entry path.

The default device client is `tracing-mcp`; `tracing-cli` and legacy Kaneo device
clients are also allowed by default. On first use, open the printed verification
URL and approve the device. New credentials use `~/.config/tracing-mcp` (or the
matching `XDG_CONFIG_HOME` directory). Existing `kaneo-mcp` credentials remain
usable for the same server. `TRACING_API_KEY` can provide an existing API key for
a headless client. Keep keys in the client's secret configuration.

## Available tools

Both the HTTP endpoint and stdio package expose the same tools:

- Session: `whoami`, `list_workspaces`, `list_workspace_members`, `list_notifications`
- Search: `search`
- Projects: `list_projects`, `get_project`, `create_project`, `update_project`, `list_project_columns`
- Tasks: `list_tasks`, `get_task`, `get_task_by_ticket_id`, `create_task`, `duplicate_task`, `update_task`, `delete_task`, `move_task`, `update_task_status`, `update_task_assignee`, `update_task_due_date`, `update_task_recurrence`, `list_task_activity`
- Custom fields: `list_project_custom_fields`, `get_task_custom_field_values`, `set_task_custom_field_value`
- Time entries: `list_task_time_entries`, `get_time_entry`, `create_time_entry`, `update_time_entry`
- Comments: `list_task_comments`, `create_task_comment`, `update_task_comment`, `delete_task_comment`
- Labels: `list_workspace_labels`, `create_label`, `attach_label_to_task`, `detach_label_from_task`, `delete_label`
- Task relations: `create_task_relation`, `get_task_relations`, `delete_task_relation`

### Planning tools

The hosted endpoint and source-built stdio server also share these planning tools:

- Project planning: `get_project_plan`, `update_project_plan`.
- Milestones: `list_milestones`, `create_milestone`, `update_milestone`, `delete_milestone`, `get_task_milestone`, `update_task_milestone`.
- Initiatives: `list_initiatives`, `get_initiative`, `create_initiative`, `update_initiative`, `delete_initiative`, `reorder_initiatives`, `add_project_to_initiative`, `remove_project_from_initiative`.
- Updates: `list_status_updates`, `create_status_update` for projects or initiatives.
- Cycles: `list_cycles`, `get_cycle`, `get_cycle_settings`, `update_cycle_settings`, `update_cycle`, `list_cycle_tasks`, `update_task_cycle`, `update_task_estimate`.

These tools require the corresponding planning features to be enabled. The API enforces the signed-in user's workspace/project permissions and API-key scopes. They do not grant extra access.

Cycles are generated, started and closed automatically. Use `update_cycle_settings` to enable them, set cadence, timezone, lookahead (`upcomingCycles`) and rollover, then `list_cycles` to find the generated IDs. This requires workspace settings permission. Changing cadence reschedules upcoming cycles. Disabling cycles closes the active cycle, deletes upcoming cycles and clears their assignments; past history and tasks remain. There is no individual manual create/start/delete operation.

Use `update_cycle` to rename any cycle or change an upcoming cycle's dates. Dates use the workspace timezone, with an exclusive end date. The API rejects overlapping ranges, changes to current/past dates and durations above eight weeks. `list_cycle_tasks` supports project, assignee, category, status, priority, label and text filters with pagination.

For milestones, `update_milestone` accepts a zero-based `position` for reordering. `update_task_milestone` accepts a milestone in the task's project or explicit `null` to unassign. Deleting a milestone clears its task assignments without deleting the tasks.

For initiatives, use `update_initiative` with `archived: true` to archive or `false` to restore. Archiving/restoring and permanent deletion require workspace settings permission. Other edits and project links require project update permission and project visibility. Removing a link preserves the project. `reorder_initiatives` takes every non-archived initiative ID exactly once; read every page first, and refresh if the API reports a conflict. An existing link can be reordered with `add_project_to_initiative` and `position`.

Omit fields to preserve their values. Use explicit `null` to clear nullable owners, dates, icons or colors, and an empty string to clear descriptions. Paginated tools return `hasMore`; continue fetching pages until it is false. Status updates can be read and posted; the API has no edit/delete status-update operation.

### Connect from Claude

Add a custom remote connector in Claude with:

```text
https://tracing.gofigureapp.io/api/mcp
```

Choose OAuth sign-in and automatic client registration if asked. Sign into Tracing and approve the connection. Enable the connector in your conversation. After a server update, refresh its tool list or reconnect if Claude still shows the old catalog.

Try: “Create a launch milestone, assign these issues to it, and post an initiative status update.” For cycles: “Show our cycle settings and upcoming cycles, then rename the next cycle.”

Use `get_task_by_ticket_id` with a key such as `KAN-12` to fetch one task directly. If the same key identifies multiple accessible tasks, pass `workspaceId` or `projectId` to select one.

`list_project_columns` is worth calling first when setting a status: the column
slugs it returns are exactly the values `create_task` and `update_task_status`
accept. Likewise `list_workspace_members` resolves the user IDs the assignee
tools expect. Time entries have no delete endpoint on the API, so there is no
`delete_time_entry` tool.

`get_task` and `list_tasks` don't include custom field values. Call
`list_project_custom_fields` for a project's field IDs, types, and options, and
`get_task_custom_field_values` for one task's values. `set_task_custom_field_value`
takes a string, number, or boolean, an array of options for a multiselect field,
or `null` to clear the value. Dates use `YYYY-MM-DD`.

## Debugging

To run the stdio server directly:

```bash
node packages/mcp/dist/index.js serve
```

When running from source in this monorepo:

```bash
pnpm --filter @tracing/mcp run build
pnpm --filter @tracing/mcp run start
```

### Teams

With `PARITY_FEATURES=teams`, both the HTTP and stdio catalogs offer
`list_teams`, `get_team`, `create_team`, `update_team`, `archive_team`,
`delete_team`, `list_team_members`, `add_team_member`, `remove_team_member`,
and `set_project_team`. Teams organize work without granting project access.
Project counts and issue/project lists include only projects the caller can read.

Keys contain two to five uppercase ASCII letters and are unique within a
workspace. Team creation, editing and deletion use `team:create`, `team:update`
and `team:delete`. Membership changes require team management permission or the
team lead; API keys additionally need `team:update`. Only existing workspace
members can be added. Archived teams retain their projects but reject new
assignments and members until restored with `archive_team` and `archived=false`.

Pass `teamId=null` to `set_project_team` to clear an assignment. Deleting a team
keeps every project and issue, clearing those projects to **No team**. Explicit
null clears a team's lead, icon or color; omitted update properties are retained.
Task identifiers stay based on the project, and task teams derive from project
ownership.

`list_workspace_tasks` accepts `team` (a team ID or `none`) and rich `team`
filters with `is` / `is-not` and nullable values. `list_projects` accepts `team`
and returns the paginated planning collection for that filter; use its `page` and `pageSize` parameters while `hasMore` is true. Filtered listings cover active projects. The unfiltered tool keeps its
existing project-list contract.
